# PDF Editor — project brief

A full-featured PDF editor delivered as ONE self-contained static HTML file (`dist/pdf-editor.html`) that works by opening it in a browser. No server, no uploads, no analytics: everything runs locally. The only network requests allowed are library loads from public CDNs.

The features, layout and behaviour closely follow the open-source desktop app PdfCraft (MIT/Apache-2.0), but the app uses NONE of its branding: no PdfCraft/ArtCraft names, no lion logo, no red tile. The product name everywhere is **PDF Editor**. Logo: a simple inline SVG of a document with a folded corner.

Work proceeds milestone by milestone (see MILESTONES.md). Only build what the current milestone asks for, but keep the architecture ready for the later ones.

## Milestone workflow (follow this exactly)

Progress is tracked in `PROGRESS.md` (create it if it's missing). It lists every milestone M0–M12, each with a status of `todo`, `in progress`, `awaiting approval` or `approved`, plus short notes: key decisions, known issues, and anything the user asked to change.

1. **At the start of every session**, read `PROGRESS.md` and `MILESTONES.md`.
   - If a milestone is `awaiting approval`, don't start new work. Remind the user what's waiting for review and how to test it.
   - Otherwise, take the first milestone that isn't `approved`.
2. **Do that milestone.** Use the prompt text in the matching code block in `MILESTONES.md` as your instructions, and plan before coding. Set it to `in progress`.
3. **When its Definition of done is met**, set it to `awaiting approval`, write its notes in `PROGRESS.md`, and commit. Then STOP and tell the user:
   - what was built
   - how to try it (open `dist/pdf-editor.html`, and what to click)
   - known limitations
   - "Reply **approved** to continue to the next milestone (<name>), or tell me what to change."
4. **If the user asks for changes**, make them, re-run the Definition of done, and ask for approval again.
5. **When the user replies "approved"** (or "continue", "next", "go", "looks good"), set the milestone to `approved`, commit, and start the next milestone immediately, from step 2.
6. Never start more than one milestone without approval. Never mark a milestone `approved` yourself.
7. Keep `PROGRESS.md` up to date, because it's the memory between sessions: if the context is cleared, everything needed to carry on must be in `PROGRESS.md`, `CLAUDE.md` and git history.
8. After M12 is approved, give a final report and stop.

## Architecture rules

- Source lives in `src/` as small ES modules plus CSS files. `build.mjs` (Node, no dependencies) inlines all CSS and JS into `dist/pdf-editor.html`. The build output is the deliverable, and it must work when opened via `file://`.
- Workers (pdf.js worker, the pdf-lib heavy-ops worker) are created from Blob URLs so the single file still works.
- Libraries are loaded from jsDelivr with pinned versions:
  - pdfjs-dist: rendering, text layer, search, outline, page labels, attachments, optional content, annotations/forms layer
  - pdf-lib: all modification and saving
  - tesseract.js: OCR, lazy-loaded only when OCR opens
  - fflate: zipping split outputs
  - (optional) a qpdf WASM build: encryption, only if a working CDN build exists
- Vanilla JS, no framework. Keep a clear split between:
  - `core/`: document model, undo/redo, the pdf-lib operations, persistence (IndexedDB)
  - `view/`: the renderer, viewport, virtualization, tiles
  - `ui/`: shell, panels, dialogs, command palette, menus
  - `tools/`: one module per tool, each registering itself in a central **tool registry** (id, label, category, shortcut, status: `ready` | `soon`, run())
  - `i18n/`: all user-facing strings (English for now)
- Every document-changing action goes through the command/undo system as a named step. No direct mutation from the UI.
- The design must survive 300+ page PDFs: virtualized pages, lazy thumbnails, and heavy work off the main thread.

## Testing rules

- `tests/fixtures/` contains PDFs generated by `tests/make-fixtures.mjs` (pdf-lib): multi-page, mixed page sizes, an outline, page labels, AcroForm fields of every type, annotations, an attachment, optional content if possible, a deliberately corrupted file, and a password-protected file (use qpdf CLI if available, otherwise skip).
- Playwright (Chromium) end-to-end tests in `tests/e2e/` run against the built `dist/pdf-editor.html`. Each milestone adds tests for its features.
- Every milestone ends with these steps: `node build.mjs`, all tests green, no console errors in a smoke test, take screenshots of new UI in light and dark themes and look at them, and fix anything that looks off.
- When a test fails, fix the code, not the test (unless the test is wrong).

## Layout (target)

1. **Top bar**: app menu (File, Edit, View, Tools, Help); a horizontal tab strip of open documents (filename, a dot for unsaved changes, a close ×; scrolls horizontally with the wheel; right-click offers Close / Close others / Reopen closed tab); a ⌘K palette button and a theme toggle on the right.
2. **Left tools panel**: resizable 240–520px; Shift+F4 toggles it; Preferences can move it to the right. Tools are grouped under: Read · Find · Organize · Combine & split · Protect · Forms & layers · Scan & OCR · Everywhere. Unbuilt tools show a "Coming soon" badge.
3. **Center viewport.**
4. **Right edge rail**, always visible, plus one side panel beside it (resizable 260–520px by dragging its inner edge; F4 toggles it). Panels: Pages, Bookmarks, Layers, Fields, Comments, Attachments, Document Properties.
5. **Find bar** (⌘F) with an "n of m" match counter, prev/next, match-case and whole-word.
6. **Status bar**: page input / total, page label, zoom % with − / + / fit width / fit page, and the current layout.
7. **Home screen** when no document is open: a drop zone with an Open button, recommended tools, recent files (IndexedDB), the privacy note "Your files never leave this device", and the full tool catalogue.

## Visual design

- A calm, compact desktop-app look, not a marketing page.
- Dark theme: base #1e2327, panels #262c31 / #2e353b, separators #3a4248, text #e6e8ea, muted #9aa3ab.
- Light theme: base #f6f7f8, white panels, separators #d9dde1, text #1e2327.
- Accent: crimson #b70228 (hover #8a011e) for primary buttons, the active tab underline, selection outlines and the focus ring.
- System UI font stack, 13px UI text, 28–32px controls, 6px radii, shadows only on popovers/modals. Inline SVG icons (Lucide-style strokes), with tooltips that show shortcuts.
- Pages sit on a neutral canvas with a soft shadow and 16px gaps. Respect prefers-color-scheme on first run, and remember the user's choice.
- All theming goes through CSS custom properties.

## Keyboard shortcuts

⌘O open, ⌘S save, ⇧⌘S save as, ⌘W close tab, ⇧⌘T reopen closed tab, ⌘P print, ⌘F find, ⌘G / ⇧⌘G next/prev match, ⌘K command palette, ⌘Z / ⇧⌘Z undo/redo, ⌘= / ⌘- / ⌘0 zoom, F4 side panel, Shift+F4 tools panel, F11 full screen, Esc to exit modes. Use Ctrl on Windows/Linux.

## Non-negotiables

- No fake features. If something can't be done properly in a browser (e.g., real encryption without a WASM library), the tool shows "Coming soon" instead of pretending.
- Never lose user work: unsaved-change guards, autosave, and recovery.
- Damaged PDFs: render the pages that work and show an error tile for the ones that fail. Never show a blank app.
- Keyboard accessible, with ARIA roles on tabs, menus, panels and dialogs.
- Help → About: "PDF Editor", a version number, the licenses of the bundled libraries, and the line "Inspired by the open-source PdfCraft project (MIT/Apache-2.0)."
